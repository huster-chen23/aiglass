# 3 分钟答辩问答准备

## 1. 为什么选择 UDP，不选择 TCP？

AR/VR 更重视实时性。UDP 不需要建立连接，也不会因为等待丢失数据重传而阻塞后续帧。即使丢失一帧，客户端仍然可以播放下一帧。TCP 虽然可靠，但丢包时可能出现队头阻塞和卡顿。

## 2. UDP 丢包后画面会怎样？

本项目不是等待丢失分片，而是设置超时机制。只要一帧没有收齐，超时后就丢弃该帧，继续接收后面的帧。因此表现为跳帧，而不是整个播放过程停止。

## 3. 为什么要自己设计分片协议？

UDP 单个数据报有大小限制，而 JPEG 压缩后的图像可能超过安全大小。如果直接发送，数据可能发送失败或产生 IP 分片。项目使用帧编号和分片序号，让客户端能够正确重组一帧图像。

## 4. UDP 如何保证分片顺序？

UDP 本身不保证顺序。本项目在每个数据包头部加入 seq 分片序号，客户端将分片放入字典，只有收齐全部分片后，按照 0 到 total-1 的顺序拼接。

## 5. 为什么 JPEG 压缩？

原始屏幕图像数据量太大，无法满足实时传输要求。JPEG 是有损压缩格式，可以显著减少带宽占用，并且 OpenCV 提供了简单的编码和解码接口，适合本实验实现。

## 6. 如何测量端到端时延？

服务端在 UDP 数据包头部写入发送时间戳，客户端收到完整帧后，用当前接收时间减去发送时间。由于本机测试时钟同步，结果可以近似表示端到端时延。

## 7. TCP 实验如何解决粘包和拆包？

TCP 是字节流，没有消息边界。本项目在每个 JPEG 帧前加 4 字节无符号长度，客户端先读取长度，再精确读取对应数量的字节，这样可以正确区分每一帧。

## 8. 50% 丢包时为什么不是完全没有画面？

本实验的每个画面在当前参数下通常是一个 UDP 数据包。丢包是随机发生的，因此大约一半帧仍能完整到达并显示。实际多分片画面中，只要任意一个分片丢失，该帧就会丢弃。

## 9. 项目的不足是什么？

当前是整帧 JPEG 方案，没有实现关键帧、前向纠错或选择性重传；TCP 模式暂时没有加入发送时间戳。工程化系统还需要更高效的视频编码器、拥塞控制和自适应码率。

## 10. 如果继续改进，你会做什么？

第一，增加关键帧和增量帧；第二，增加 FEC，减少少量丢包造成的整帧丢失；第三，根据网络状况自动调节分辨率、JPEG 质量和帧率；第四，用 Mininet 系统比较不同延迟和丢包率下的 UDP、TCP 性能。
