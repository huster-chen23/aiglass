# AI 智能眼镜 · 一个月五人并行开发计划

## 0. 目标定位：对标现役真实产品

对标市面已量产的 Ray-Ban Meta、小米 AI 眼镜，抽取其**核心功能闭环**作为一个月的可达成目标：

> 第一视角拍摄 → AI 识别 → 语音播报结果，同时画面实时传到手机/电脑（我们已有的 UDP 图传底座）。

一个月交付的是**能戴、能演示的工作原型**（工作台级，不追求量产外观），采用"功能闭环优先、外观其次"的原则。

技术路线双保险：
- **主路线**：安卓手机 + 绑带改造（摄像头/屏幕/麦克风/电池全内置，最快闭环）
- **备路线**：树莓派 Zero 2W + 摄像头 + 微型显示（更接近真机形态，调通后可替换）

---

## 1. 五人分工：每人一个板块，全程并行

| 成员 | 板块 | 独立交付物 | 对应已有基础 |
|---|---|---|---|
| **A** | 网络与实时图传 | 摄像头→眼镜第一视角→接收端实时画面，端到端 < 200ms | 现有 server.py / protocol.py 直接复用 |
| **B** | 硬件与显示终端 | 可佩戴的终端：屏幕点亮、续航 ≥ 1h、结构可戴 | 无（采购+装配） |
| **C** | 语音交互链路 | 按键说话 → 文字 → 语音回答，全程 < 2s | 无（ASR/TTS API） |
| **D** | 视觉 AI 识别 | 摄像头画面 → 目标检测/OCR → 文本结果，单帧 < 500ms | OpenCV 经验复用 |
| **E** | 系统集成与测试 | 接口协议、控制总线、联调报告、答辩材料 | 实验报告/PPT 经验 |

**并行原则**：A 不等 B 的硬件（先在电脑+手机上跑通），D 不等 C（先各自出 demo），E 从第 1 天就定接口，所有人对着同一协议开发。

## 2. 四周计划与每周验收标准

### 第 1 周：方案冻结 + 各自 POC
| 人 | 任务 | 周末验收 |
|---|---|---|
| A | 摄像头接入替代屏幕捕获；手机热点直连图传 | 无线图传跑通，延迟 < 300ms |
| B | BOM 采购下单；手机方案点亮屏幕 | 终端能显示接收画面 |
| C | Whisper/FunASR + TTS API 跑通 | 说话→文字→语音回复 |
| D | YOLOv8 + PaddleOCR 在 PC 上跑通 | 摄像头画面实时标出物体 |
| E | 冻结接口协议 v1；建 Git 仓库与每日站会 | 协议文档 + 各模块 mock 通过 |

### 第 2 周：五模块并行开发
- A：延迟优化到 200ms 内，加自适应码率（丢包率→降质量）
- B：佩戴结构（3D 打印镜架/绑带）、电池供电方案、散热
- C：PTT 按键触发 + 唤醒逻辑，识别结果接 TTS
- D：模型部署到端侧或边缘电脑，压缩到单帧 < 500ms
- E：实现控制总线（TCP + JSON），用假数据串起 A/D/C
- **验收**：每个模块可独立演示

### 第 3 周：系统集成联调（E 主导）
- 贯通全链路：**按键 → 拍摄 → D 识别 → C 播报**，同时 **A 图传**到接收端
- B 完成整机装配；E 建立 bug 看板，每 48h 一次集成烟测
- **验收**：全链路演示打通一次不中断

### 第 4 周：优化、组装与验收
- A：弱网（Mininet 限带宽/丢包）测试报告
- B：外观收尾，续航实测
- C：嘈杂环境语音测试
- D：识别准确率抽样评测（>80% 常见物体）
- E：延迟/功耗数据表、5 分钟演示脚本、答辩 PPT 更新
- **验收**：戴上眼镜完整演示 5 分钟 + 数据报告 + 答辩

## 3. 接口协议（E 第 1 周冻结，全员遵守）

媒体通道沿用现有 UDP 分片协议（protocol.py）；控制通道为 TCP + JSON：

```json
{"type": "capture_req",  "from": "button",  "ts": 1730000000}
{"type": "ai_result",    "from": "vision",  "labels": ["bottle", 0.91], "ts": 1730000001}
{"type": "tts_req",      "from": "fusion",  "text": "这是一瓶矿泉水"}
{"type": "heartbeat",    "from": "display", "battery": 0.62, "latency_ms": 180}
```

消息只有 4 种类型，新增字段向后兼容；所有模块 E 提供对应 mock，互不阻塞。

---

## 4. 协作机制（并行不乱的关键）

1. **接口先行**：E 第 3 天给出协议 v1 + 每个模块的 mock，之后只改字段不加类型
2. **每日 15 分钟站会**：只说三件事——昨天完成/今天计划/阻塞点
3. **每 48 小时一次集成烟测**：哪怕只有两个模块真实、其余 mock，也要跑通主干
4. **Git 分支模型**：main（可演示）/ dev（集成）/ feature-各人；合 dev 必须 E 审
5. **共用看板**：任务卡分 待办/进行中/待联调/完成 四列

## 6. 风险与 Plan B

| 风险 | 应对 |
|---|---|
| 硬件延期/不亮屏 | 主路线手机方案兜底，B 先出手机绑带版 |
| 端侧推理太慢 | D 退到"边缘电脑推理+WiFi 传输结果"，画面仍在眼镜 |
| ASR 不准 | C 加按键 PTT（按住才识别）+ 常用词热词表 |
| 无线带宽不足 | A 降分辨率/帧率，UDP 自适应已有基础 |
| 集成冲突 | E 的 mock 机制保证任何人被阻塞时其他四人不停工 |

## 7. 最终演示脚本（答辩当天）

1. 队员戴上眼镜，按下镜腿按钮："这是什么？"
2. 眼镜拍摄前方桌面 → D 识别 → 2 秒内耳机播报："这是一瓶矿泉水，旁边是手机"
3. 评委看向大屏：眼镜第一视角实时画面（UDP 图传）+ 识别框叠加
4. E 展示数据表：图传延迟、识别耗时、续航、弱网表现
5. 一句话收尾："这就是我们在一个月内、五个人并行完成的 AI 眼镜核心闭环。"
